# Промпт для проверки CQA перед сдачей

Проверь текущий проект CQA после последних изменений. Выполни проверки и представь доказательства, а не только рекомендации. Сохрани React-интерфейс и рабочие функции. Не добавляй новые возможности и не начинай общий рефакторинг.

## Правила и исходное состояние

1. Прочитай AGENTS.md, README.md, web/README.md, reports/условие.md, reports/задачи.md, reports/чек-лист.md. Условие и правила команды главнее общих советов.
2. Сверь текущее время с часовым поясом Asia/Almaty. PR до 09:00 воскресенья 08.11.2026, контрольный час в 11:00, стоп-код в 12:00. После стоп-кода исходники не меняй.
3. Зафиксируй ветку, HEAD, origin/main и незакоммиченные изменения. Разрешён git fetch для чтения актуального состояния. Не перезаписывай чужие или уже сделанные изменения. Не делай reset --hard, stash, force push, прямые изменения main. Коммит, push и PR только по отдельному запросу. Перед будущим PR потребуется git merge origin/main и повтор проверок; проверка сама по себе не является подготовкой PR.
4. Сделай отдельную временную копию текущих исходников с учётом незакоммиченных файлов. Исключи .git, .env, реальные data/outputs, пользовательские .DS_Store, node_modules и окружения. Сравни SHA256 исходников, чтобы проверялась именно текущая версия.
5. Не меняй без согласования app/checklists/freedom_chat_v1.json, app/evaluator/prompt.py, app/scoring/. Не добавляй пакеты и не меняй версии зависимостей. Зафиксируй исходные хеши защищённых файлов и манифестов.
6. Не вызывай платные модели и API организаторов. Приложение запускать только с mock-провайдером, env_file=None на тестовых стендах, вымышленными диалогами и отдельной временной SQLite. Не использовать пользовательскую рабочую базу для тестовых записей.
7. Не выводи в чат реальные транскрипты, секреты, подписанные URL и цитаты из настоящих диалогов. Артефакты браузера сохраняй вне git. В тестах только явно вымышленные данные.

## Проверки

1. В изолированной копии выполни npm ci --ignore-scripts, npm run build, npm run typecheck, npm test. Проверь, что lock-файлы не изменились. Запусти полный Python pytest в подготовленном окружении с PYTHONUTF8=1. Если переиспользуется окружение, явно укажи это; не называй такой запуск установкой с нуля.
2. Запусти приложение из этой копии и проверь health: provider и model должны быть mock. Сравни хеш отданной браузеру сборки с собранным файлом.
3. В настоящем браузере пройди:
   - загрузку корректного JSON, пустого и повреждённого файла, пустого transcript, повторную загрузку;
   - одиночную и пакетную оценку, подтверждение, прогресс, запрет двойного запуска, частичный сбой и повтор только ошибочных;
   - доказательства и исходную нумерацию реплик, N/A, нулевой балл, грубую ошибку, неполную оценку;
   - апелляцию, решение человека, пересчёт, исходную и финальную оценку, сохранение после перезагрузки;
   - изменение чек-листа через UI и применение нового критерия без правки кода, сохранность исторической версии;
   - историю запусков, старую ссылку и отчёт, сравнение одной версии, отказ на чужой ID/несовместимые снимки, фильтр изменений, ошибки и повтор чтения;
   - аналитику: среднее только полных результатов, отдельный учёт грубых ошибок с applicable:false, исключение N/A и неизвестных ответов, фильтры языков/версий, честную пустую выборку;
   - выгрузку исходных/финальных DEV и PROD, дубли/пропуски/посторонние ID, запрет сдачи mock/demo, отсутствие цитат и секретов в публичном результате;
   - HTTP503/неверный формат API, отсутствие скрытой подмены на demo, восстановление задания и черновики;
   - RU/EN/KK, кириллицу, казахские символы, HTML/спецсимволы, печатный отчёт/PDF, ширины320/390/768/1440.
4. Используй существующие browser-*.js и tests/*_server.py, разделяя стенды: изменение чек-листа одним сценарием не должно менять предусловия другого. Каждый сценарий запускай на подходящей свежей базе/контексте. Не выдавай перехваченный API за интеграцию с настоящей SQLite.
5. Проверь ошибки JavaScript и отсутствие незапланированных внешних запросов. Для проверок «этого нет» нужен положительный контроль, где элемент/запрос/данные есть.
6. Независимо проверь контракт выгрузки и безопасность текущих изменений. Любая находка должна иметь воспроизведение, файл/строку, влияние и приоритет; предположения помечай отдельно. Не повторяй уже исправленные замечания как новые.

## Исправления

Исправляй только воспроизведённые дефекты небольшими изменениями в разрешённых файлах до стоп-кода. Сначала добавь регрессию, покажи её падение на дефекте, затем исправь и повтори затронутые проверки. Для защищённого модуля подготовь воспроизведение и запрос согласования, независимые проверки продолжай. Все новые надписи сразу RU/EN/KK. Если дефектов не найдено, исходники не меняй.

## Результат

Сохрани отчёт в reports/: проверенный HEAD и хеши копии/сборки, выполненные команды и фактические результаты, какие браузерные сценарии прошли, подтверждённые и исправленные ошибки, ограничения, оставшиеся действия до сдачи и список изменённых файлов. Отдельно укажи незакоммиченные изменения и необходимость интеграции с origin/main перед PR.

Не утверждай, что проект лишён всех возможных ошибок или гарантированно пройдёт отбор. Mock-проверка подтверждает работу системы, но не точность настоящей модели. Не заявляй готовность без реального прогона. Ничего не публикуй и не отправляй организаторам.
