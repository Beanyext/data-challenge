# CQA: оценка качества диалогов операторов

**Команда SeeUSoon** · участники на GitHub: [Beanyext](https://github.com/Beanyext), [BekmuratY](https://github.com/BekmuratY), [Seeuagaen](https://github.com/Seeuagaen), [Temerlan04](https://github.com/Temerlan04)

Решение кейса Freedom Broker на Data Challenge 7–8.11.2026. Система читает транскрипт чата или звонка и оценивает оператора по чек-листу. По каждому критерию она даёт ответ, объяснение и номера реплик-доказательств. Баллы, перераспределение весов и итог считает код, а не модель. Оценку можно оспорить: апелляция меняет ответ по критерию, итог пересчитывается.

Условие и наше понимание задачи: [reports/условие.md](reports/условие.md). Чек-лист и правила подсчёта: [reports/чек-лист.md](reports/чек-лист.md). План работ: [reports/задачи.md](reports/задачи.md). Правила работы с репозиторием: [AGENTS.md](AGENTS.md).

## Как это работает

```
диалог → запрос из настроек чек-листа → Claude → проверка ответа → подсчёт баллов → результат
```

1. **Запрос собирается только из чек-листа** [app/checklists/freedom_chat_v1.json](app/checklists/freedom_chat_v1.json): названия критериев, допустимые ответы, условия N/A, пояснения. Под конкретные диалоги в коде ничего нет. Новый критерий добавляется в настройках, без правки кода.
2. **Модель отвечает по строгой схеме** (structured outputs): по каждому критерию ответ из разрешённых вариантов, объяснение и доказательства «номер реплики + цитата». Схема устроена одним списком `criteria`, поэтому её размер не зависит от числа критериев.
3. **Код проверяет ответ** ([app/evaluator/validate.py](app/evaluator/validate.py)): каждая цитата должна найтись в указанной реплике, ответ должен быть допустимым для критерия. При ошибке модель переспрашивается один раз, потом критерий помечается «нужна проверка» для человека.
4. **Баллы считает код** ([app/scoring/score.py](app/scoring/score.py)). Критерии с N/A исключаются, веса остальных перераспределяются до 100. Счёт точный, через дроби, округление половины вверх: обычный `round()` в Python на проверочном примере D дал бы неверный итог. Грубая ошибка отмечается отдельно и итог не меняет.

Почему так:
- **Модель без дообучения.** В наборе 65 диалогов: для обучения своей модели этого мало, а чек-лист описан словами. Модель, которая читает чек-лист и диалог, переносится на новые критерии без переобучения.
- **Арифметика в коде.** Модель ошибается в счёте и округлении, код нет. Подсчёт покрыт тестами на семи проверочных примерах из [reports/чек-лист.md](reports/чек-лист.md).
- **Доказательства проверяются кодом.** Объяснение со ссылкой на несуществующую реплику ловится до того, как его увидит человек.

## Точность

Эталона организаторов у нас нет, поэтому часть DEV разметили сами: 25 чатов в [reports/gold.json](reports/gold.json). Из них 10 отложены с самого начала (seed 42): на них запрос не настраивали, они изображают контрольный этап. Метрика: доля совпавших ответов по критериям, 8 критериев на диалог.

| Часть | Диалогов | Ответов | Совпало | Ошибка итогового балла, в среднем |
|---|---|---|---|---|
| Отложенная | 10 | 80 | 98,8% | 1,88 балла из 100 |
| Настроечная | 15 | 120 | 98,3% | 0,97 балла |

Воспроизвести без вызова модели, по сохранённому файлу результатов:

```bash
.venv/Scripts/python.exe -m app.accuracy --results results/dev/results.json --split all --show-holdout
```

Как подбирали ([reports/experiments.csv](reports/experiments.csv), только настроечная часть). Первый запуск с чек-листом организаторов дал 95,8%. Расхождения разобрали и записали толкования спорных мест в пояснения критериев c02, c03, c04, c07, c08: стало 99,2%. Потом сравнили модели на одном и том же запросе:

| Модель | Совпало |
|---|---|
| `claude-opus-5-5`, effort high | 99,2% и 98,3% в двух запусках |
| `claude-sonnet-5-5`, effort high | 89,2% |
| `claude-haiku-5-5` | 87,5% |

**Честная оговорка.** Разметку сделал ИИ-помощник команды по тем же правилам, что записаны в чек-листе, а не эксперты организаторов. Цифра показывает согласие модели с этим разметчиком. Как разметка делалась и где были спорные случаи, записано в [reports/чек-лист.md](reports/чек-лист.md). Звонки в контроле не участвуют и не размечены.

## Модель и стоимость

- `claude-opus-5-5` через Claude API, глубина рассуждений `high`, один вызов на диалог, повтор только при ошибке проверки.
- Весь DEV, 65 диалогов: $2,84, в среднем **$0,044 за диалог** с учётом всех вызовов. Источник: `outputs/eval/<папка>/summary.json`, который пишет команда оценки.
- 65 диалогов в 5 потоков оцениваются примерно за 3,5 минуты.
- Модель меняется настройкой `CQA_MODEL` без правки кода.

Интерфейс CQA находится в [`web/`](web/README.md): диалоги, оценка с доказательствами, редактор чек-листа и апелляции. Запуск и контракт подключения к серверу описаны в его README.

**Проверка формулировки критерия.** В редакторе чек-листа кнопка «Проверить формулировку с ИИ» отправляет модели текст критерия и названия соседних критериев, без диалогов. Модель отвечает, можно ли по этому тексту однозначно поставить ответ: нет ли расплывчатых слов, задано ли условие N/A, не повторяет ли критерий другой. Она же предлагает формулировку яснее. Чек-лист меняется, только если пользователь подставит предложение и сохранит версию. Код: [app/server/criterion_review.py](app/server/criterion_review.py), маршрут `POST /api/checklists/review-criterion`, глубина рассуждений `CQA_REVIEW_EFFORT` (по умолчанию `medium`). В проверке 08.11 один совет стоил $0,030 и занял 16 секунд; цену и время каждого совета интерфейс показывает рядом с ним. В тестовом и учебном режимах вместо модели работают простые правила.

## Установка

Нужен [uv](https://docs.astral.sh/uv/). На Windows:

```bash
uv venv --python 3.12 .venv
uv pip sync requirements.lock --require-hashes --only-binary :all: --python .venv/Scripts/python.exe
```

`requirements.lock` собран для Windows. На другой системе:

```bash
uv venv --python 3.12 .venv
uv pip install -r requirements.in --only-binary :all: --exclude-newer 2026-10-23 --python .venv/bin/python
```

Настройки лежат в `.env` в корне, он не попадает в git. Образец без секретов: [.env.example](.env.example). Нужны `ANTHROPIC_API_KEY` и `CQA_API_URL`, адрес API организаторов с подписью.

Все команды ниже запускаются из корня репозитория, перед ними один раз `export PYTHONUTF8=1`.

## Запуск

**Сервер и интерфейс.** API на FastAPI, данные в SQLite (`outputs/server/cqa.sqlite3`, переживает перезапуск).

```bash
.venv/Scripts/python.exe -m uvicorn app.server.main:app --host 127.0.0.1 --port 8000
```

- Интерфейс: `http://127.0.0.1:8000/`, сервер отдаёт папку `web/`. Описание API: `http://127.0.0.1:8000/api/docs`.
- Настоящие диалоги открывать без `?demo=1`: в учебном режиме загруженный файл остаётся в браузере. «Печать / PDF» сохраняет полный транскрипт, такие файлы держать в `outputs/`, не в git.
- `CQA_PROVIDER=mock` включает тестовый режим без модели и без расходов.
- Загрузка диалогов: `POST /api/dialogs/import` с `{"group_id": "DEV"}`.
- Уже сделанные оценки (папка `outputs/eval/<папка>` от `app.evaluator.cli`) загружаются в базу без вызова модели: `.venv/Scripts/python.exe -m app.server.load_evals --evals outputs/eval/<папка> --data data/raw/dev.json`. Так ноутбук готовится к показу бесплатно, новые диалоги на показе оцениваются вживую.
- Сервер слушает только `127.0.0.1`. Интерфейс на другом порту указывается явно в `CQA_CORS_ORIGINS`.

**Оценка из командной строки.**

```bash
.venv/Scripts/python.exe -m app.data_api DEV --out data/raw/dev.json
.venv/Scripts/python.exe -m app.evaluator.cli --data data/raw/dev.json --ids p1-ru-007 --provider mock
.venv/Scripts/python.exe -m app.evaluator.cli --data data/raw/dev.json --workers 5 --out outputs/eval/dev
```

**Файл результатов** в формате организаторов (JSON 1.0) и его проверка:

```bash
.venv/Scripts/python.exe -m app.results build --data data/raw/dev.json --evals outputs/eval/dev --out results/dev/results.json --team "Название" --expect 65
.venv/Scripts/python.exe -m app.results check results/dev/results.json --data data/raw/dev.json --expect 65
```

**Контрольный этап** одной командой: загрузка группы, оценка, повтор неудавшихся, сборка и проверка файла.

```bash
.venv/Scripts/python.exe -m app.results control --group-id <ID> --out results/prod/results.json --expect 10
```

**Разметка эталона.** Локальная страница, ответы пишутся в `reports/gold.json`:

```bash
.venv/Scripts/python.exe -m app.razmetka
```

**Тесты.**

```bash
.venv/Scripts/python.exe -m pytest -q
```

## Что не попадает в git

В наборе реальные диалоги, а репозиторий открытый. Поэтому в git нет транскриптов, записей звонков, цитат из них, адреса API организаторов и ключей: всё это лежит в `data/`, `outputs/` и `.env`. Исключение по требованию организаторов: файлы `results/*/results.json`. В них только оценки, номера реплик и объяснения пересказом. Дословные цитаты при сборке файла заменяются на «…».
