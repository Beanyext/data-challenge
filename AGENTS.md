# Правила проекта Data Challenge

Для всех ИИ-помощников команды (Claude Code и Codex) и для людей.

## Порядок работы

1. **Условие.** Читать `reports/условие.md` и `reports/задачи.md` и сверять с ними каждое решение. Главный критерий отбора: точность оценки относительно эталона организаторов.
2. **Правила о данных.** ИИ на этом хакатоне разрешён полностью, данные можно показывать ИИ-помощникам. В наборе есть реальные звонки, а репозиторий будет открытым: транскрипты, записи, цитаты из них и адреса с подписью `sig` в git не кладём, адрес API организаторов хранится только в `.env`. Исключение по требованию организаторов: `results/dev/results.json` и `results/prod/results.json` лежат в git. В них только оценки, номера реплик и короткие объяснения пересказом, без дословных цитат и личных данных. Если в условии или описании данных окажется отдельное ограничение (соглашение о неразглашении, персональные данные), остановиться и сказать команде. Тогда строки данных не выводить, потому что вывод команд уходит модели.
3. **Контракт и срез.** Сначала форматы из раздела «Контракт» в `reports/задачи.md`, потом сквозной путь на одном диалоге.
4. **Разметка.** Ручные оценки части DEV заменяют эталон. 10 размеченных диалогов откладываем: на них запрос не настраиваем, они изображают контрольный этап.
5. **Контроль.** Новый критерий и новые диалоги проходят через интерфейс без правок кода. Запрос к модели собирается только из настроек чек-листа. Никаких заранее готовых результатов и логики под конкретные диалоги.
6. **Улучшения.** Одна гипотеза, один запуск, строка в `reports/experiments.csv`. Сравнивать с разметкой по критериям и по итогу. Прибавка меньше разброса между запусками не считается улучшением.
7. **Сдача.** Запуск заново на чистой копии. Подробности в разделе «Сдача и показ».

## Команды

Все команды запускать из корня репозитория, перед ними один раз: `export PYTHONUTF8=1`. Полный список с пояснениями в `README.md`.

```bash
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m app.data_api DEV --out data/raw/dev.json
.venv/Scripts/python.exe -m app.evaluator.cli --data data/raw/dev.json --ids p1-ru-007 --provider mock
.venv/Scripts/python.exe -m app.accuracy --evals outputs/eval/<папка> --log "имя эксперимента"
.venv/Scripts/python.exe -m app.results control --group-id <ID> --out results/prod/results.json --expect 10
.venv/Scripts/python.exe -m uvicorn app.server.main:app --host 127.0.0.1 --port 8000
```

Данные лежат в `data/raw/`, оценки модели пишутся в `outputs/eval/`. `data/` и `outputs/` в git не попадают.

## Проверенные ловушки этой машины

Всё ниже воспроизведено 07.11.2026 на Windows, Python 3.12.

- **Схема ответа модели.** Схема с отдельным свойством на каждый критерий не компилируется уже на 8 критериях: API отвечает 400 «compiled grammar is too large». Держать один список `criteria`, размер схемы не должен зависеть от числа критериев.
- **Сервер на Windows.** Если ответить на запрос, не дочитав его тело, Windows обрывает соединение и клиент получает ошибку сети вместо ответа. Тело читать до любого ответа, как в `app/razmetka/server.py`.
- **Кодировка.** `python -I` игнорирует `PYTHONUTF8`, вместо него `-X utf8`. `csv.writer` на Windows пишет концы строк CRLF, передавать `lineterminator="\n"`.
- **Новые версии библиотек:** anthropic 2.2, fastapi 0.162, starlette 1.9. Синтаксис по памяти может не работать, документацию сверять через context7.

## Качество

- Зерно случайности 42. Итоговый результат считается командой из репозитория.
- Каждая цифра в презентации воспроизводится командой из репозитория. Цифр по памяти нет.
- Коммит на каждый проверенный шаг: что изменилось и какая получилась оценка.
- Не коммитить данные организаторов, ключи и пароли.

## Сдача и показ

Готовим с первого часа, а не в последний. Если условие требует другого, главнее условие.

**Выяснить сразу и записать в `reports/условие.md`:**
- что сдаём: файл ответов, код, отчёт, презентацию, ссылку на репозиторий;
- куда и до какого времени, с часовым поясом;
- сколько попыток и какая считается итоговой;
- как проходит показ: сколько минут, вживую или записью, на чьём компьютере, будут ли вопросы жюри.

**Доступ к коду.** Условие требует открытый репозиторий и ссылку организаторам до стоп-кода. Сейчас он приватный. Открытие показывает всем всю историю коммитов и почту авторов, поэтому сначала проверяем историю на ключи и данные. Открывает владелец репозитория, срок указан в `reports/задачи.md`.

**Показ.**
- Интерфейс по условию на HTML, CSS и JavaScript. Заранее проверить подключение ноутбука к экрану.
- Хотя бы один диалог оцениваем вживую: организаторы проверяют, что система действительно анализирует новые диалоги, а не показывает готовое.
- Запасной вариант: скриншоты и запись экрана на случай, если живой запуск не сработает.
- Каждый участник может своими словами объяснить метрику, проверку и главный вывод.

**Перед сдачей.**
1. За час до срока новых гипотез не начинаем, только доводим и проверяем.
2. Свежая копия: `git clone` в пустую папку, установка по README, `pytest`, запуск приложения, оценка одного диалога. Так видно, что ничего не зависит от файлов, которых нет в git.
3. В README описать задачу, результат и как его воспроизвести.
4. Поставить метку на сданный коммит и запушить её: `git tag submission-1`, затем `git push origin submission-1`.
5. Сдаёт один заранее названный человек. ИИ-помощник сам ничего не сдаёт, не пишет организаторам и не открывает репозиторий.

## Работа в git

- `main` всегда рабочий: скрипты запускаются, `pytest` зелёный. Прямо в него не коммитить и не пушить. Технически GitHub этого не запретит: защита веток в приватном репозитории недоступна на бесплатном тарифе, правило держится на нас.
- У каждого участника своя копия репозитория и своя ветка `имя/что-делаю`. Ветка живёт часы, а не дни.
- ИИ-помощник работает только в ветке своего участника и чужие ветки не трогает. Два помощника в одной папке мешают друг другу, для второй задачи нужна отдельная копия или `git worktree`.
- Обновлять ветку через `git merge origin/main`. Переписывать историю и пушить с `--force` нельзя.
- Перед вливанием: `git merge origin/main`, `pytest`, затем PR. Вливаем сразу, как только тесты зелёные.
- Чтобы не мешать друг другу, каждый пишет в свой модуль в `app/`. Общие модули (`app/scoring/`, `app/evaluator/`) правятся маленькими отдельными коммитами.
- `requirements.lock` меняет один человек за раз и предупреждает остальных.
- В git не попадают данные, `outputs/`, ноутбуки, CSV и ключи (см. `.gitignore`). Обходить это через `git add -f` нельзя.
- Журнал `reports/experiments.csv` сливается автоматически: строки всех участников сохраняются.
- Каждую сданную версию отмечать меткой и пушить её: `git tag submission-1`, `git push origin submission-1`.

## Новые пакеты

Список закреплён в `requirements.lock` с хешами и датой отсечения 2026-10-23. Новый пакет добавлять в `requirements.in`, затем:

```bash
uv pip compile requirements.in --python-version 3.12 --python-platform windows --only-binary :all: --generate-hashes --exclude-newer 2026-10-23 --no-header -o requirements.lock
uv pip sync requirements.lock --require-hashes --only-binary :all: --python .venv/Scripts/python.exe
```

Посмотреть изменения в `requirements.lock` до установки. Пакеты вне PyPI и без готовых сборок не ставить.
